# AthleteVision AI — Database

PostgreSQL database schema for the AthleteVision AI platform.

The database stores athlete information, uploaded video metadata, AI-generated performance metrics, talent scores, and AI-generated performance reports.

---

## 1. Database Overview

AthleteVision AI follows this data flow:

```text
User
  │
  │ 1:1
  ▼
Athlete
  │
  │ 1:N
  ▼
Video
  ├── 1:N ──► Performance Metrics
  │
  ├── 1:1 ──► Talent Score
  │
  └── 1:1 ──► Performance Report
```

The database is designed around the video as the central entity for AI analysis.

An athlete can upload multiple videos. Each video can have multiple performance metrics, one talent score for the MVP, and one performance report.

---

## 2. Technology

* PostgreSQL 16+
* UUID primary keys
* JSONB for flexible AI-generated data
* Foreign key constraints
* Check constraints
* Unique constraints
* Automatic timestamps
* PostgreSQL `pgcrypto` extension for UUID generation

## 3. Database Structure

### 3.1 Users

Stores authentication and basic user information.

| Column          | Type         | Description                     |
| --------------- | ------------ | ------------------------------- |
| `id`            | UUID         | Primary key                     |
| `name`          | VARCHAR(100) | User name                       |
| `email`         | VARCHAR(255) | Unique email                    |
| `password_hash` | TEXT         | Hashed password                 |
| `role`          | VARCHAR(20)  | ATHLETE, COACH, SCOUT, or ADMIN |
| `created_at`    | TIMESTAMPTZ  | Creation timestamp              |
| `updated_at`    | TIMESTAMPTZ  | Last update timestamp           |

---

### 3.2 Athletes

Stores athlete-specific information.

| Column       | Type         | Description             |
| ------------ | ------------ | ----------------------- |
| `id`         | UUID         | Primary key             |
| `user_id`    | UUID         | Foreign key to `users`  |
| `sport`      | VARCHAR(100) | Sport played by athlete |
| `position`   | VARCHAR(100) | Playing position        |
| `location`   | VARCHAR(255) | Athlete location        |
| `bio`        | TEXT         | Athlete biography       |
| `created_at` | TIMESTAMPTZ  | Creation timestamp      |
| `updated_at` | TIMESTAMPTZ  | Last update timestamp   |

Relationship:

```text
users 1 ───── 1 athletes
```

Each athlete is associated with one user account.

---

### 3.3 Videos

Stores metadata for athlete-uploaded videos.

The actual video file is intended to be stored in Amazon S3. PostgreSQL stores the metadata and S3 object key.

| Column             | Type         | Description                                |
| ------------------ | ------------ | ------------------------------------------ |
| `id`               | UUID         | Primary key                                |
| `athlete_id`       | UUID         | Foreign key to `athletes`                  |
| `filename`         | VARCHAR(255) | Original filename                          |
| `s3_key`           | TEXT         | S3 object key                              |
| `video_url`        | TEXT         | Optional video URL                         |
| `status`           | VARCHAR(30)  | UPLOADED, PROCESSING, COMPLETED, or FAILED |
| `duration_seconds` | NUMERIC      | Video duration                             |
| `uploaded_at`      | TIMESTAMPTZ  | Upload timestamp                           |
| `processed_at`     | TIMESTAMPTZ  | AI processing completion timestamp         |

Relationship:

```text
athletes 1 ───── N videos
```

Example S3 key:

```text
videos/{athlete_id}/{video_id}/original.mp4
```

The `s3_key` is the canonical reference to the video stored in S3.

---

### 3.4 Performance Metrics

Stores metrics generated by the AI service.

The table uses a flexible metric structure so new metrics can be added without changing the database schema.

| Column         | Type         | Description             |
| -------------- | ------------ | ----------------------- |
| `id`           | UUID         | Primary key             |
| `video_id`     | UUID         | Foreign key to `videos` |
| `metric_name`  | VARCHAR(100) | Name of metric          |
| `metric_value` | NUMERIC      | Metric value            |
| `unit`         | VARCHAR(50)  | Metric unit             |

Relationship:

```text
videos 1 ───── N performance_metrics
```

Example:

```text
metric_name        metric_value       unit
------------------------------------------------
max_speed          24.5               km/h
distance_covered   1200               meters
acceleration       3.2                m/s2
```

This structure allows the AI service to return different metrics without requiring database schema changes.

---

### 3.5 Talent Scores

Stores the overall AI-generated talent score.

The MVP score is between 0 and 100.

Current scoring categories:

| Category               | Weight |
| ---------------------- | -----: |
| Speed                  |    30% |
| Agility                |    25% |
| Ball / Skill Control   |    25% |
| Movement / Positioning |    20% |

| Column            | Type         | Description                            |
| ----------------- | ------------ | -------------------------------------- |
| `id`              | UUID         | Primary key                            |
| `video_id`        | UUID         | Unique foreign key to `videos`         |
| `score`           | NUMERIC(5,2) | Overall score from 0–100               |
| `version`         | VARCHAR(50)  | Scoring algorithm version              |
| `score_breakdown` | JSONB        | Individual category scores and weights |
| `created_at`      | TIMESTAMPTZ  | Creation timestamp                     |

Relationship:

```text
videos 1 ───── 1 talent_scores
```

Example `score_breakdown`:

```json
{
  "speed": {
    "score": 85,
    "weight": 0.30
  },
  "agility": {
    "score": 80,
    "weight": 0.25
  },
  "ball_control": {
    "score": 90,
    "weight": 0.25
  },
  "movement_positioning": {
    "score": 75,
    "weight": 0.20
  }
}
```

The `version` field allows the scoring algorithm to change in the future without losing information about which version produced a score.

---

### 3.6 Performance Reports

Stores the AI-generated performance report.

Reports can be generated using Gemini or another supported LLM.

| Column            | Type         | Description                    |
| ----------------- | ------------ | ------------------------------ |
| `id`              | UUID         | Primary key                    |
| `video_id`        | UUID         | Unique foreign key to `videos` |
| `summary`         | TEXT         | Overall performance summary    |
| `strengths`       | JSONB        | Identified strengths           |
| `weaknesses`      | JSONB        | Identified weaknesses          |
| `recommendations` | JSONB        | Training recommendations       |
| `metrics_summary` | JSONB        | Summary of important metrics   |
| `model_version`   | VARCHAR(100) | AI model/version used          |
| `generated_at`    | TIMESTAMPTZ  | Report generation timestamp    |

Relationship:

```text
videos 1 ───── 1 performance_reports
```

Example:

```json
{
  "strengths": [
    "Good maximum speed",
    "Strong ball control"
  ],
  "weaknesses": [
    "Agility can be improved"
  ],
  "recommendations": [
    "Practice acceleration drills",
    "Include cone-based agility exercises"
  ]
}
```

JSONB is used because the number and structure of strengths, weaknesses, and recommendations may evolve.

## 10. Database Testing

The schema has been tested using sample data covering the complete relationship.

Test flow:

```text
User
  ↓
Athlete
  ↓
Video
  ↓
Performance Metrics
  ↓
Talent Score
  ↓
Performance Report
```

The following database rules have been verified:

* Primary keys work correctly.
* Foreign keys work correctly.
* One user can have one athlete profile.
* One athlete can have multiple videos.
* One video can have multiple performance metrics.
* One video has one talent score for the MVP.
* One video has one performance report for the MVP.
* Talent scores outside the range 0–100 are rejected.
* Duplicate talent scores for the same video are rejected.
* Duplicate performance reports for the same video are rejected.
* JSONB data is stored and retrieved correctly.
* JOIN queries can retrieve the complete athlete analysis.

## 11. Current MVP Constraints

The current schema intentionally keeps the design simple for the MVP.

### Talent Score

One video has one current talent score:

```text
videos 1 ───── 1 talent_scores
```

The `version` column allows future scoring algorithms to be identified.

### Performance Report

One video has one current performance report:

```text
videos 1 ───── 1 performance_reports
```

This can be changed later if the system needs multiple reports per video or multiple report versions.

## 12. AWS Storage Integration

Video files should not be stored directly inside PostgreSQL.

Recommended architecture:

```text
                  ┌──────────────────┐
                  │   Spring Boot    │
                  └────────┬─────────┘
                           │
                Upload video
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
       ┌───────────┐               ┌───────────┐
       │    S3     │               │PostgreSQL │
       │Video File │               │ Metadata  │
       └───────────┘               └───────────┘
             │                           │
             │                           │
       Actual video                 s3_key
```

PostgreSQL stores:

```text
video_id
filename
s3_key
status
duration
timestamps
```

Amazon S3 stores:

```text
actual video file
```

The S3 bucket should remain private. Presigned URLs can be used when temporary access to a video is required.

## 16. Development Notes

* Do not commit database passwords or credentials.
* Do not commit AWS access keys.
* Use environment variables or a secret-management solution for credentials.
* Keep the S3 bucket private.
* Use UUIDs when creating new application records.
* Keep `s3_key` as the persistent reference to S3 objects.
* The AI service should return metrics in a clearly defined API contract.
* Database schema changes should be communicated to the backend team before integration.
